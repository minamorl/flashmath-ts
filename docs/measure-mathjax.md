# MathJax 4.1.3: macro 展開時の入力再構築の計測

この環境・入力集合では、既定上限内の `\newcommand` ケースの再構築区間は **warm p50 で全体の 0.219〜0.820%**、cold p50 で 0.514〜1.718% だった。区間には計器の費用が含まれ、後続の遅延処理は含まれないので、再構築を除去したときの短縮率とは扱わない。

H1 はこの観測範囲で支持する。H2 の「入力長×展開回数が時間の支配項になる」という読みは支持されなかった。**「毎回残り全部をコピーするので二次時間になる」という性能上の主張は捨てる。** 残りの長さの総和と、V8 が実際に処理する bytes / 時間を区別する。

## 実行環境と結果

実測期間は **2026-11-07 02:24:37〜02:37:33 JST**（raw の `startedAt`〜最後の worker の `recordedAt`）。再開確認後の集計ファイル生成は 02:38:48 JST。Node **v26.12.1**、V8 **14.6.202.34-node.40**、MathJax **4.1.3**、Temml **0.14.0**。Linux x64、kernel `7.0.0-38-generic`、AMD Ryzen 5 3600 6-Core Processor、利用可能 logical CPU は12。`NODE_ENV=production`、`NODE_OPTIONS` は未設定。

共有ホストで CPU affinity と周波数固定は行っていない。load average (1/5/15分) は開始時 11.02 / 16.42 / 16.49、再開確認後の終端集計時 45.20 / 31.74 / 23.39。ばらつきが大きく、絶対時間やライブラリ間の倍率を専用ホストの性能値へ一般化しない。特に p95 と独立 process 間の差は scheduling、GC、JIT と切り分けられない。

### H1 / H2 と計算量の判定

**H1: 限定して支持。** 成功した default の macro 五条件で、区間率の warm p50 はすべて1%未満、warm p95 は最大1.521%。この区間が TeX→MathML の wall time の主因である証拠はない。引数なしで `x` に展開する今回の入力集合についての結論であり、任意の macro に対する上限保証ではない。

**H2: 積に比例する支配的コストモデルは支持しない。** P=0 で N を64→4096にすると、suffixUnits は 6112→25163776（約4117倍）だが、MathJax warm p50 は 2.275→112.494 ms（約49.4倍）、区間 p50 は約0.015→0.734 ms。N=4096 のまま P を0→32768にしても、suffixUnits は約6.33倍に対し、区間は約1.22倍、全体は約1.67倍だった。同じ長さの inline 全体も約1.73倍になっており、長い入力の増分を macro 再構築だけへ帰属させることはできない。

長い macro 入力で全体が遅くなる弱い意味の傾向はある。しかし対照との差が負になる条件もあり、この共有ホストの独立 process の中央値の差から、再構築の純粋な因果寄与率を推定する精度はない。Temml の時間との差も、異なる parser・MathML 生成・付加属性などを含むため、そのまま再構築の費用ではない。

**計算量について残すのは suffix 長の総和の式だけ。** eager copy を仮定すれば `O(展開回数 × 残りの最大長)` という作業量モデルは書けるが、`slice` と `+` の実装がそれを毎回実コピーするという前提を今回の観測は与えない。有限の測定で漸近上界を証明・反証したとも主張しない。V8 の cons/sliced string と遅延 flattening の仮説とは整合するが、内部表現を観測していないため、これを実証された原因とはしない。

計器の診断として、成功した macro 条件ごとの warm「区間 p50 / 呼出し回数」は179〜346 ns/回、中央値299 ns/回。空の timer pair の条件別中央値は90〜131 ns、中央値120 nsだった。差し引き補正はしていない。同条件の計測版/通常版の全体 p50 比は warm で0.903〜1.245（中央値1.064）、cold で0.823〜1.445。計器や共有ホストの変動は、区間率で扱っている小さな値に対して無視できず、「0.820% が正確な削減可能量」といった読み方はしない。

今回の観測値は「小さい直接区間費用」と「大きい全体時間・ばらつき」を分けて示す。区間外の遅延コピー・GC まで含めた純粋な因果寄与率は未同定であり、そこを決めるには出力と意味を保存した実装の比較、または文字列内部と allocation の追加観測が必要である。

## 再現

リポジトリのルートで、既存の依存を使って次の一コマンドを実行する。外部通信、依存の追加、`node_modules` の書き換えは行わない。

```sh
NODE_ENV=production node bench/mathjax/run.mjs
```

既存の `bench/mathjax/results/runs.jsonl` があれば同じ条件・round の記録を飛ばして再開する。コード、入力、対象ソースの hash、ライブラリ版、Node/V8、`NODE_OPTIONS` が違えば再開を拒否する。新規に測り直す場合は、同じコマンドの末尾に `bench/mathjax/results-rerun` のような未使用の出力先を指定する。同じ出力先で複数の実行を同時に走らせない。

各 worker の終了直後に JSONL の一行を追記し、flush する。中断で最終行だけが不完全になった場合、その bytes を `interrupted-tail.bin` に残し、最後の worker を再実行する。途中の行の破損、重複 task、再開条件の不一致を成功として扱わない。round ごとの snapshot と全測定の終了時に `raw.json` を書く。

- [`../bench/mathjax/results/runs.jsonl`](../bench/mathjax/results/runs.jsonl): worker ごとの再開用 journal。cold 一回と warm 五回を含む。

## 測定の境界

MathJax は CommonJS 版の `TeX` を `packages: ['base', 'newcommand']` で作る。`mathjax.document` に input jax だけを渡し、`doc.convert(tex, {display: true, end: STATE.COMPILED})` の内部 MathML tree を `SerializedMmlVisitor.visitTree` で文字列にする。output jax、SVG、CHTML、レイアウト、DOM への描画、フォント取得は含めない。各変換の直前の `tex.reset()` は測定に含む。

Temml は `renderToString(tex, {displayMode: true, throwOnError: true, ...limits})` を使う。同じ TeX を渡すが、MathML の整形、付加属性、対応機能は同一ではない。この比較を macro 展開の方式だけの因果比較にはしない。

全 worker は `NODE_ENV=production`。一つずつ同期的に起動し、harness 自身による並列測定を避ける。条件は入力・上限・engine の組。各条件で fresh Node process を五本使う。

- **cold n=5**: import と jax/document 作成後の最初の変換。process 起動と import/setup は含めず、setup の時間は別途保存する。「モジュール読込も含む cold start」の値ではない。
- **warm n=25**: 各 process で cold のあと十回を捨て、続く五回を保存する。JIT の定常状態を保証するものではない。五つの process に cluster した観測であり、25本の独立 process ではない。
- 単位は ms。quantile は nearest rank (`sorted[ceil(p*n)-1]`)。cold の p95 は n=5 の最大値なので、母集団の p95 の精密な推定には使わない。
- 明示的 GC は入れない。GC、JIT、OS の scheduling は wall time に含まれる。
- 出力は MathML 文字列が返った時点までを計時する。hash 計算、`data-latex` 属性を除いた正規化、返却文字列の追加消費は時間外。V8 が後から行う文字列処理まで含むとは限らない。
- エラーも同じ回数を記録するが、成功した TeX→MathML の時間から分ける。MathJax は `formatError` で throw させ、`<merror>` を成功として数えない。

## 入力と上限

`ordinary` は 16 / 64 / 256 / 1024 code units。`x^2+\frac{1}{y}+` を繰り返して `x` で終え、指定長まで空白で埋める。16文字ケースは `x` と空白15文字であり、小さい式の基準である。ASCII だけなので code units と文字数は等しい。

`macro-nN-pP` は `\newcommand{\a}{x}`、`\a ` を N 回、P 個の空白、最後に `y`。N は 64 / 256 / 768 / 1536 / 4096、P は 0 / 4096 / 32768。`inline` は定義と macro 呼出しを空白と `x` に置き換え、**入力長と出力トークン数を合わせた**対照入力。N と P の直積で、展開回数と、各展開のあとに残る入力長を別々に変える。

入力は `repeat` と連結で生成し、事前に flat string にする処理は強制していない。同じ worker 内では同じ入力文字列を再利用する。cold と warm の違いには JIT/cache に加えて、入力文字列の内部表現が初回の処理で変わった効果も入り得る。JSON から毎回新しく取り出した文字列、非 ASCII、引数付き・再帰的な macro、大きな展開結果については、この結果だけで一般化しない。

MathJax の出力には `data-latex` / `data-latex-item` がある。通常版と計測版の出力 hash はそのまま一致を要求する。macro と inline の比較は、この二つの属性だけを除いた文字列の hash 一致を要求する。ライブラリ間の MathML の意味的同値性を判定する conformance test は、この harness の範囲に含めない。

| 条件 | MathJax maxBuffer | MathJax maxMacros | Temml maxExpand |
|---|---:|---:|---:|
| default | 5120 | 1000 | 1000 |
| raised | 1048576 | 100000 | 100000 |

default では上限値を明示上書きせず、既定を使う。MathJax の実効値は worker 起動時にも検証する。`maxBuffer` は `addArgs` の生成文字列長のチェックであり、すべての入力の初期長を5120文字に制限する検査ではない。長い inline 入力の成功を、macro 入力も通る根拠にはしない。

補助の `template-probe` は区切り引数付き `\def`、`environment-probe` は `\newenvironment` の site を通す。Temml 0.14.0 は `\newenvironment` を未サポートとしてエラーを返す。これは上限超過とも成功時間とも分ける。

## 再構築区間の計時と限界

対象は `BaseMethods.Macro`、`NewcommandMethods.MacroWithTemplate`、`NewcommandMethods.BeginEnv` にある次の組:

```js
parser.string = ParseUtil.addArgs(parser, expansion, parser.string.slice(parser.i));
parser.i = 0;
```

`mathjax` と別に `mathjax-instrumented` の process を起動する。CommonJS loader hook で、インストール済みソースの上記三か所だけに `process.hrtime.bigint()` を前後挿入する。各置換がちょうど一か所であること、三か所すべてがロードされたことを検証し、ロード後に hook を外す。インストール済みファイルの変更や再実装への差し替えはない。hook の対象と元ソースの SHA-256 は raw に残す。

区間には `slice`、`addArgs` の境界正規表現・maxBuffer 検査・結合、`parser.i = 0` が入る。引数の取得と代入、`substituteArgs`、`checkMaxMacros`、後続のパースと MathML 直列化は入らない。呼出し回数と suffix 長の加算は区間外であり、計測版の全体時間には入る。

表の区間率は、**同じ計測版 sample の区間合計 / 全体時間 × 100** の分位点。区間 ms の p50 と全体 ms の p50 を割って求めない。これは通常版の真の因果寄与率でも、処理をなくしたときの speedup でもない。

二つの clock read の差にも計器の費用が含まれる。各 worker の終了時に空の timer pair を256回測り、raw に残すが、測定区間から機械的に差し引かない。JIT と呼出し文脈が異なるためである。計器による最適化の変化、allocation、GC、区間の外で遅延して起こる cons string の flattening は分離できない。区間時間が小さくても、文字列操作が後続処理に与えた費用がゼロだとは結論しない。

`suffixUnits` は参照した残りの長さの和であり、実際にコピーした bytes ではない。この入力集合では、成功した N 回の展開について正確に

```text
S(N,P) = 3*N*(N-1)/2 + N*(P+1)
```

になる。`GetCS` が macro 呼出しの直後の空白を消費することを織り込んだ値で、raw の計数と一致することも検査する。V8 が `slice` を共有参照で保持したり、結合を cons string にしたりする可能性があるため、S をコピー量や処理時間のモデルとして採用するには別途証拠が必要である。

## 検証

`bench/mathjax/check.mjs` は小さい実入力で、三つの site、default の buffer/展開上限のエラー、raised の成功、出力の一致、入力長、suffix 計数、分位点を検証する。結果検査器が不正な成功・出力 drift・欠落を拒否することも確認する。検査器確認のための複製した観測は、本測定の raw には入れない。

`bench/mathjax/check-journal.mjs` は保存後の再読込、metadata の維持、重複・異なる条件の拒否、不完全な最終行の退避と復旧、途中の破損の拒否を確認する。全測定終了時にも validator が全条件・round の欠落、出力の不一致、想定外の成功・エラーを検査する。

`node bench/mathjax/verify-results.mjs` で、journal と raw の一致、対象ソースと harness の hash、metadata と時系列、summary と全条件表の再計算、本文のすべての数値表と artifact link を検証できる。実行したコマンドと出力は [`evidence.txt`](../bench/mathjax/evidence.txt) に残した。測定終了前の round snapshot を検査した際は未完の一巡分を `Missing runs` として拒否し、終了後の全 raw で検査を通した。

再開確認の前後で `runs.jsonl` の SHA-256 はどちらも `7b1311a32da20e40625aebeb4bd4f313038d6f50b873326985b3eb1d80420861`。再測定せずに全 worker を読み戻し、raw と表を再生成した。

一次資料はインストール済みの `@mathjax/src/ts/input/tex.ts`、`base/BaseMethods.ts`、`newcommand/NewcommandMethods.ts`、`ParseUtil.ts`、`core/MmlTree/SerializedMmlVisitor.ts`、Temml の `src/Settings.js` と `src/MacroExpander.js`。API と既定上限はこの版のソースで確認した。
