## Cause and visible decisions

At base db71e2f, `src/output.ts:96–100` changes parser-marked `mpadded` labels to
natural-width `mrow`s, retaining only horizontal padding. `src/output.ts:112`
unconditionally drops the final `mspace` from every recognized label. That
removes the upper depth strut (`src/packages/ams.ts:328`,
`src/packages/mathtools.ts:126`, `src/packages/extpfeil.ts:19–27`). Chromium's
italic ink can descend outside the token's layout box, so the remaining Core
spacing does not prevent the descender from reaching the arrow. The existing
DOM-rectangle test misses this ink outside its rectangle.

The same-condition control changes only this strut: with its removal, the
reported `f` intersects the arrow's vertical ink envelope; retaining a minimum
native depth clears it without changing horizontal layout. This identifies the
lost depth, rather than a missing positive voffset, as the cause. Upstream's
upper voffset is negative, not a simple upward translation.

The fix is `src/output.ts:115–120`: retain the nonempty upper strut with a native
minimum depth of `.3em`. A `.2em` restoration, and then `.25em`, still failed the
new 32px inherited-serif case (gaps −.75px and −.25px respectively). The `.3em`
minimum passes. Keep dropping the existing lower strut; its Core layout already
clears the ink. Preserve the horizontal padding and empty-label lowering,
including empty extpfeil labels. Parser output and `output:'mathjax'` remain
unchanged; no dependency, lockfile, API, fixture-conformance, or unrelated
production change was made. `package.json` and README now declare 0.1.2.

`bench/native-render/xarrow-ink.mjs`, not by the implementation being tested.

test still renders the actual long commands. Bounds allow .25em above and .4em
below plus .75px for different TeX/DejaVu arrowhead and one-sided harpoon bearings.
These are geometric tolerances, not a claim of font/pixel identity.
